# Pre-publish audit, 2026-10-08

Scope: `main` after merging `batch-a` and `claude/batch-b-0rk7j6`. Four read-only reviews
(server remotes and security, saves and DataStores, Robux and Roblox policy, runtime errors and
performance), then fixes, then the full offline regression suite. Offline only: nothing here
was tested in Studio, on a live server or on a real phone.

Result: no publish blocker found. The fixes below are in `main`.

## 1. Merge

- `batch-a` and `main` had fixed the same things in parallel (tutorial bubble placement,
  danger-arrow keep-out, starter card subtitle, walkthrough replay). Clashes were resolved by
  taking batch A's versions, which were the later, fully re-tested pass.
- The owner's holds were kept. These switches are off: DailyQuests, StarterBundle, GroupBonus,
  InviteRewards, FinalStand, StageModifiers, PartyQuickLines, Prestige and QuickResume.
- The StarterBundle / GroupBonus / InviteRewards logic checks and the social Home-card layout
  checks need their switch on, so they are out of the regression list until release (the
  same as batch B's held checks).

## 3. Owner decisions (left as they are)

1. **Robux Revive prompt opens by itself on death.** RunManager `onDowned` shows the revive
   offer and also opens the Roblox purchase dialog with no tap. Roblox allows this, but an
   automatic prompt at the moment of death can feel pushy and covers NO THANKS. Option: open
   the dialog only when REVIVE is tapped. This was owner-verified in Studio earlier, so it is
   unchanged.
2. **Store items read "Coming soon".** All cosmetic, hero and skin product ids are 0 until
   the owner creates them. The store is honest about it. Option: hide OPEN STORE until at
   least one id is set.
3. **Movement speed check is loose.** An exploiter can move about 2.4x speed (and drift while
   frozen) before the server corrects them. Tightening it without a Studio or phone test risks
   rubber-banding real players on a bad connection. Suggest tightening after a live test.
4. **Paid power vs. the "never pay-to-win" rule.** Revive and the VIP reroll (owner kept them),
   and the DoubleGold / StarterPack gold multipliers, are in-run or economy boosts bought
   with Robux. Runs that used them still reach the leaderboards. Option: say so in the rules,
   or keep paid-revive runs off the boards.

## 4. Checked and clean

- Every remote goes through `Remotes.Listen`, which applies rate limits and pcall. Arguments
  are type- and range-checked. There are no RemoteFunctions.
- DEV access is decided on the server. DEV taint keeps boosted runs off boards and records.
- Rewards are paid exactly once: quests, comeback gift, streak, season, revive thanks, the
  walkthrough chest, chests and the merchant.
- Receipts are idempotent and saved before PurchaseGranted. Id 0 products are never prompted.
- There are no paid random items. Premium chests cost run gold only, so no PolicyService odds
  check is needed.
- Player text (bug reports) is filtered before storage. There are no HTTP calls and no secrets
  on the client.
- Held features are inert on the server and the client.
- Saves:
  - Loads that fail never start a fresh profile.
  - Session lock and autosave are in place.
  - BindToClose saves every player.
  - Studio uses the `_Studio` stores.
  - Schema 7 migrations are a chain, and every new field has a default.
  - Save tables are capped.
